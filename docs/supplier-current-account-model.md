# 供应商往来、结算与成本调整模型

状态：2026-09-06，以下保留完整目标模型。供应商往来第一阶段已落地，实际已实现范围、操作与限制以 [实施说明](supplier-current-account-implementation.md) 为准；下文未实现的未来场景不能视为当前功能。

适用范围：单店内部进销存，使用者为老板、店长、员工、仓库员。供应商是往来单位，不新增供应商登录端。本方案管理经营往来，不替代正式财务总账和税务凭证；含税成本、税额及正式记账期间需结合门店实际会计口径确定。

## 一、结论与当前缺口

不能继续用“采购金额 - 已付款”代表全部供应商关系。需要建立供应商双向往来账，并将进退货、货款确认、实际收付、抵扣核销、成本调整分开记录、相互关联。

用户已明确：有赊购，有供应商调价后补偿门店的情况。以下流程是据此提出的完整设计，不代表每家供应商都采用同一协议。

当前代码核对结果：

| 位置 | 当前行为 | 无法覆盖的情况 |
| --- | --- | --- |
| `server/src/erp.js:158`，`purchase` | 采购与全部入库同时发生，供应商只保存名称；未传付款额时默认全额付款 | 独立下单、提前付款、分批到货、同名供应商区分 |
| `server/src/erp.js:587`，`finance` | 按供应商名称合计采购金额减已付款 | 供应商欠门店、预付款、限制用途的抵扣额度 |
| `server/src/erp.js:610`，`paySupplier` | 一笔付款对应一张采购单，不允许超过待付货款 | 合并付款、多付留存、供应商退款、往来抵扣 |
| `server/src/erp.js:227`，`deduct` | 串码商品取单件成本，普通商品取移动平均成本 | 后续调价的成本追溯与已售成本调整 |

这不是增加一个“欠款方向”字段就能完成的功能，但也不需要为了单店引入完整大型财务 ERP。

## 二、必须分开的五件事

| 业务事实 | 回答的问题 | 关键边界 |
| --- | --- | --- |
| 货物流转 | 订了、到了、收了、退了多少货 | 未到货、待验货、可售、待退货不能混为一个库存数量 |
| 往来确认 | 谁对谁承担了多少款项 | 采购计划、补差申请不直接变成已确认账款 |
| 实际收付 | 钱何时从哪个账户进出 | 供应商同意退款，不等于微信或银行已经到账 |
| 抵扣核销 | 这笔钱或额度抵了哪些单 | 一笔付多单、一单分次付；抵扣不是新增收付款 |
| 成本归属 | 这笔调整影响哪些货和销售 | 改参考进价、改变库存成本、调整已售成本是不同动作 |

付款与单据分离、以后再关联结清，是成熟 ERP 的常见做法；Odoo 官方文档支持独立付款、部分付款和多单合并付款。本项目借鉴这种结构，不照搬其完整会计界面。[Odoo 付款与匹配文档](https://www.odoo.com/documentation/17.0/applications/finance/accounting/payments.html)

补充两个容易混淆的点：

- 下单后还没到货、也没付款，不一定已经形成确认的应付款；按合同或双方确认的付款义务记录。建议普通门店采购以验收和结算确认作为常用节点，合同约定先付的款项另行支持；货物所有权在运输途中何时转移也按约定，不用“到了店里”替代所有判断。
- 市场降价或下一批采购价下降，不会自动让供应商欠钱。只有已有协议明确产生的补偿权利、或供应商确认的补差，才能入已确认往来；申请中或有争议的金额单列，不能直接用来少付货款。

## 三、老板应该看到哪些余额

供应商详情常用余额分四类，全部显示未结部分，不只给一个正负数：

| 页面名称 | 含义 | 能否当现金使用 |
| --- | --- | --- |
| 我待付货款 | 门店已确认、尚未结清的货款或约定费用 | 是付款义务；可区分到期日 |
| 对方应退/应付款 | 对方已经确认应付给门店、尚未付清的现金款 | 有明确现金结算权利，到账前仍不是门店现金 |
| 预付货款余额 | 已打给供应商、尚未核销的购货款 | 能否退回、能否跨订单使用按协议 |
| 仅抵货款额度 | 已确认但不能退现金的补差或返利额度 | 仅在指定供应商、商品或期间内抵扣 |

同一金额不能同时记在两类余额中。可退款的补差如果也允许抵货款，仍只记一笔，并标记两种可选结算方式；不能再复制一笔抵扣额度。预付款转为已确认退款款项时，也需要转类，不能两边都保留。

“本次可抵扣”是从上述款项中按条件筛出的计算结果，不是另外一笔资产。页面可以显示“抵扣后建议付款”，但抵扣确认前保留原始待付和可用款项；确认后两端余额同步减少。

保证金、押金若实际存在，另设往来用途及到期退还条件，不默认当可抵货款预付款。往来总览可加“保证金余额”次级行，不能为凑四个数字而错误归类。

同一个往来单位可同时向店里供货、又从店里买货；采用稳定 ID 识别结算主体，名称和收款账户作为资料。不同公司、不同个人的账不能因为都叫某个渠道而自动合并抵扣。

## 四、完整业务场景

| 场景 | 货物与往来处理 | 成本和资金处理 |
| --- | --- | --- |
| 到货付清 | 验收入库，确认货款，关联本次付款结清 | 入库成本与实际付款分别记录 |
| 先货后款、赊购、月结 | 验收后按约定形成应付款，可分次付、多单一起付 | 未付不妨碍记录已取得货物的成本；到期日不等于确认日 |
| 先付一部分或全款、后到货 | 未核销付款保留为预付款；到货确认货款后抵用 | 未收货时不能凭付款直接增加可售库存 |
| 部分到货、少货、错货、破损 | 记录实际验收、拒收、待处理数量；剩余可继续到货或终止 | 未收到部分不假入库；预付款保留或根据确认结果转退款 |
| 多送货、搭赠商品 | 区分补发、正式买入、赠送和代管；先明确归属再入可售库存 | 买赠若构成组合采购，按明确规则分摊总成本，不能一律把赠品视作无成本利润 |
| 暂估进价，后来最终结算 | 原收货不删除，追加核价差额；区分录错更正与后续商业调价 | 调整对应库存或已售/耗用成本，并增加或减少往来 |
| 降价、库存价保、批次补差 | 按协议范围确认补差，区分申请额与认可额 | 只调符合条件的货；可退现金还是仅抵货款分别记录 |
| 双方同意追补涨价或撤回不符合条件的补差 | 依据原进货或原补差确认追加应付/扣回 | 不因市场涨价自动加成本；处理关联成本和已用额度 |
| 采购退货，原货款未付 | 退货物流与退款约定分别确认，形成一笔可用于结清原货款的退货贷项 | 抵扣原应付；不能再为同额另外生成一笔现金应收 |
| 采购退货，已经付清或部分付清 | 经确认的退货款可退现金或抵其他进货；未付与已付部分分别结清 | 实际退款到账才产生资金收入；退货成本与退款差额需有原因 |
| 同型号保修换机 | 旧串码返厂/待换，新串码接替，保留成对关系 | 无买卖结算的换机不能虚增采购、销售额；成本按换货约定承接 |
| 不同型号换货、升级补款 | 明确退旧、入新、补付或退回差额 | 关联两端货物及成本，不能只改商品名称或串码 |
| 不退货但质量折让 | 保留实物，确认供应商给的折让 | 属于采购价折让的调成本；修理费报销或损失赔偿按业务性质分开 |
| 月度/季度销量返利、活动补贴 | 预计、达标待确认、已确认分开；保存活动和适用范围 | 采购折让、推广服务报酬、费用报销不能全部当作同一类利润 |
| 运费、代垫费、手续费 | 保存承担方、实际付款方和结算对象 | 购货直接费用与经营费用按口径区分；代垫不重复当收入或费用 |
| 多付款、重复打款、部分退款 | 多出部分保持未核销款；退回时关联原付款 | 不能为了消掉差额而伪造进货或把付款额改小 |
| 尾差、抹零、双方同意不再结清 | 独立记录调整额、原因、批准人和所结款项 | 不直接手改供应商余额，也不伪造实际到账 |
| 同行向门店调货 | 若为真实买卖，走门店销售，形成对方购货欠款 | 不冒充采购退货；同主体双方同意后可与进货款抵扣 |
| 借机、寄售、铺货 | 区分货在店内和货归门店所有；按协议在买断/售出时结算 | 不能把代管库存直接当自有赊购库存；未使用时后续再做专门页面 |
| 老板个人代付、第三方代收代付 | 标明实际付款人、收款人、供应商和对应单据 | 供应商债务可以结清，但不能虚构店铺微信或现金账户减少；店铺与代付人的往来另记 |
| 供应商同时也是运营商渠道 | 单位总览可合并查看，来源仍区分进货与号卡业务 | 复用已有运营商佣金应收，不重复生成一遍；员工提成仍是另一种业务 |

供应商退回配件、维修耗材的补差同样进入本模型。维修仍是普通销售，实际耗材发生变化或后来获得价差，要追溯到该次维修销售，而不是重新建立独立维修收入账。

## 五、调价怎样影响成本

### 1. 调价单必须说明什么

每次调价确认保存：供应商、协议/活动编号、原进货单及明细、商品、批次或串码、适用数量、原结算价、调整后价或每件差额、申请金额、确认金额、证明附件、确认人、结算方式及使用限制。

三个日期分别保存：适用截止日、业务确认入账日、实际收付日。截止日还在库存的手机，可能到补差确认时已经卖掉；资格判断看约定截止日，成本去向看该件货后续实际流转，不能只查询今天的库存数量。

同一协议明确是“补到目标价”还是“额外再减多少钱”；重复导入、重复点确认不得多补一次。连续两次调价只记录各自应补差额，不能每次都拿最初进价重复全额计算。

### 2. 用手机举例

示例，非门店真实数据：向甲供应商进 10 台手机，每台 2,000 元，货款 20,000 元，已经付 12,000 元。甲确认本批次 10 台全部每台补 100 元；其中 6 台仍在自有库存，4 台已卖出，无退换货及其他调整。

| 时点 | 我待付 | 已确认补差未结 | 本次实际现金变动 |
| --- | --- | --- | --- |
| 已入库并付 12,000 元 | 8,000 元 | 0 元 | 支出 12,000 元 |
| 确认补差 1,000 元，尚未抵扣 | 8,000 元 | 1,000 元，性质按协议 | 0 元 |
| 双方同意将 1,000 元全部抵货款 | 7,000 元 | 0 元 | 0 元 |
| 再付剩余 7,000 元 | 0 元 | 0 元 | 支出 7,000 元 |

成本方向独立计算：6 台库存各减 100 元，库存价值减少 600 元；4 台已售成本合计减少 400 元。原销售收入不变，关联销售的调整后毛利合计增加 400 元。剩余 600 元不是当日已实现销售毛利，而是以后卖出时体现为更低的成本。

如果协议只补调价截止日符合条件的 6 台库存，补差总额就是 600 元，不补那 4 台已售手机。如果原货款已全部付清，1,000 元则留下待退现金或仅抵货款额度，不能自动认为已到账。

与购货价格有关的折扣、返利影响购货成本，是这里的核算参考；IAS 2 也区分库存成本和售出时确认的成本。本方案仅借鉴原则，不据此认定该门店适用 IFRS 或替代其会计处理。[IAS 2 购货成本条款](https://www.ifrs.org/content/dam/ifrs/publications/pdf-standards/english/2021/issued/part-a/ias-2-inventories.pdf)、[IAS 2 官方概述](https://www.ifrs.org/issued-standards/list-of-standards/ias-2-inventories/)

### 3. 串码商品与普通商品不能使用同一种简化推算

- 手机、需要串码管理的号卡：保存单件取得成本、供应商、原进货明细及后续调整，沿串码追踪销售、退货、换货；不覆盖最初采购价和销售时快照。
- 普通配件：当前是移动加权平均成本。后续必须补齐收货来源及成本流转依据；不能拿当前某 SKU 总数量，假装知道其中有多少件来自某个供应商。
- 对混合多次进货、期间多次销售的移动平均商品，精确追溯可能需要按时间重演成本流，生成库存、销售及耗材差额分配。旧销售快照保留，差异另记；不能暗中改成先进先出，或直接把全部补差压到剩余库存。
- 现有历史来源不足时，显示不能自动分配的金额，由授权人员确认有依据的分配或单列采购价差；不得编造批次和串码。首版自动化优先覆盖来源清楚的串码及简单批次，复杂普通商品需要单独验收。
- 补差金额超过可合理调整的库存价值时，不能产生负库存成本；检查业务分类、已售/耗用部分和前次调整，而不是截断金额后丢掉差额。

SAP 的移动平均价文档也专门处理存货覆盖不足时的价差归属，说明“全部差额直接改当前均价”并不可靠。本项目采用什么成本分配算法需明确验证，不默认复制 SAP 的会计科目方案。[SAP 移动平均价与存货覆盖](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/5e23dc8fe9be4fd496f8ab556667ea05/bef1d353ca9f4408e10000000a174cb4.html)

### 4. 退货、返利与成本不能重复算

获得价保后再向供应商退货，依据最终约定确认退货金额，检查是否需要退回原补差。不能既按 2,000 元全价退款，又无依据保留该台 100 元补差。

客户退回已经调过成本的商品时，要同时考虑原销售成本及其关联调整，恢复合理库存价值，并按退款后的资格处理补差。供应商返利若附有“不退货”“达到销量”等条件，也可能产生后续扣回。

采购退货的退款额和账面出库成本不一定完全相同，差额必须有核价、折让或其他明确原因。不得用退款金额强行覆盖库存成本。

对确属购货折让的返利调整成本；对推广服务费、真实费用报销、赔偿等按各自业务记录。这里的分类判断需要看协议，不把“供应商打来的钱”统一记作其他收入。[IFRIC 关于折扣与返利性质的讨论](https://www.ifrs.org/content/dam/ifrs/supporting-implementation/agenda-decisions/2004/ias-2-discounts-and-rebates-nov-04.pdf)

## 六、收付款与抵扣规则

付款先记录真实日期、金额、账户、交易凭据和供应商，再关联一个或多个待结单；一张待结单可被多次付款、退货贷项或补差抵扣结清。核销额不得超过来源可用额或目标未结额。

同供应商待付 4,000 元，确认可退现金且可抵扣的退货款 6,000 元：抵扣后待付为 0，对方应退 2,000 元。不能显示为“已付款 6,000 元”，也不能仍保留对方应退 6,000 元。

先付 10,000 元、分批收到已确认货款 6,000 元的商品：核销后预付款还剩 4,000 元，待付 0 元。不能同时列欠货款 6,000 元和已经结清而未减掉的预付款 10,000 元。

供应商只付回部分退款时，减少对应待退款，剩余继续保留。单纯撤销核销只解除款与单的关联，不凭空生成反向现金；原转账真的退回时再记实际退款。

采购价保单、退货贷项、现金记录、核销记录各有来源标识。一个业务影响只入账一次，不通过在多个页面重复修改余额实现联动。补差已被使用后撤回，需要处理原抵扣关系及重新形成的未结额，不允许直接删除补差记录。

## 七、对员工工资和老板报表的影响

用户已确认的工资规则不变：销售完成月份计提，销售退货在退货月份扣回；老板与所有店长可以设置底薪及商品提成规则。

供应商补差是否补提成尚待确认，不能默认从成本调整直接重算已确认或已发工资。

建议在补差确认界面先展示关联销售的毛利变化及可能的提成差异，再由老板按选定政策确认。若决定补发，追加关联原销售的提成调整，计入获准调整月份，保留原销售规则和原工资快照；按件提成通常不因成本变化而变，按毛利提成才可能变化。

若采用补发政策，计算方式应是“按原规则算出的调整后应计提成 - 该销售已累计计提及调整金额”，还需结合有效销售数量与退货。不能简单用“补差金额 × 当前提成比例”，尤其原销售亏损时提成为零、此前已经补过提成或商品部分退货时。

报表建议分三种口径，避免混为一个利润数：

| 视图 | 展示内容 |
| --- | --- |
| 原销售单 | 销售时收入、成本、毛利及提成快照；旁列后续成本调整与调整后毛利 |
| 当期经营日报/月报 | 当期销售及当期确认的已售/耗用成本调整分别列示；库存成本减少不直接全算当日利润 |
| 资金与往来 | 实付供应商、实收退款、无现金抵扣、期末未结款分别展示 |

按确认期展示调整的内部经营报表，与按原销售归属回看调整后毛利的分析报表不能混合相加。历史锁定期间、会计差错更正和正式财务期间处理另定规则，不静默修改旧日报和已确认工资。

## 八、状态与权限

用独立状态表达不同进度：

- 收货进度：未收、部分收货、全部收货、剩余终止；退货出库及供应商收货另有物流记录。
- 补差/退货款确认：草稿、待确认、部分确认、已确认、已冲销；申请或争议金额不混入已确认可抵额。
- 结算进度：未结、部分结清、已结清。确认欠款与是否实际付款分开。

供应商不登录系统，由店内授权人员根据双方已确定的协议、对账单或沟通凭据登记确认。已确认记录以冲销或追加调整更正，不允许直接改掉历史金额。普通录入校验、权限和防重复属于基本正确性，不新增用户暂不需要的异常预警模块。

建议权限如下，尚未获得用户对供应商资金权限的最终确认：

| 角色 | 日常定位 |
| --- | --- |
| 老板 | 看全部往来；确认期初、付款退款、抵扣、成本调整、抹零及权限授权 |
| 店长 | 维护供应商、准备采购、核对账款和补差；涉及资金与成本的确认动作按独立授权开放 |
| 仓库员 | 登记实际收货、串码、少货、退货出库、换机及附件；不自行确认供应商赔款或改往来余额 |
| 员工 | 继续正常销售；不默认可见供应商资金、采购成本及全店往来 |

所有店长能设置工资规则，不自动意味着所有店长都能抹掉供应商欠款；这两组权限必须独立。

## 九、小程序操作体验

### 供应商列表与详情

在“收支账款”内增加“供应商往来”。列表用紧凑行展示名称、我待付、对方应退，预付与仅抵额度放次级行；不堆多个大卡片，不只用正负号或颜色区分欠款方向。

详情上方保留余额摘要，下面为“往来明细、待结款项、进退货、调价补差”。常用动作是“付款、收退款、抵货款”，调价和对账放相应页签；手机屏幕内不一次塞满所有按钮。

明细点开能回答：因哪张单产生、什么时候谁确认、已用多少、抵了哪些单、还剩多少。搜索支持供应商名称、商品关键字、进货单号和串码。

### 普通进货仍然简单

常见操作仍为“选供应商 -> 选商品/扫串码 -> 填实收数量和进价 -> 选择未付/本次付款”。系统在一次确认中生成相互关联的收货、货款和付款记录，用户不必手动填写多张财务单。

先打款后收货，从供应商详情记“预付货款”，实际到货时自动带出可用预付额供确认；不要求先建一笔假入库。部分收货保留剩余待收，不强制将原单全收。

### 调价补差

选供应商后搜索商品，选择原批次或串码，选择“约定库存范围/指定批次含已售/指定串码”，填写每件差额或确认总额；适用范围必须与协议一致，不默认全店所有同名商品。

确认前给出一份结果预览：覆盖多少件、补差多少、库存成本变化、已售/耗用成本变化、形成哪类款项、若选择抵扣后还需付多少，以及待决定的员工提成影响。没有来源依据的成本分配显式留待处理，不显示虚假的精确结果。

### 付款与对账

付款可勾选多张待结单，系统提供按到期日分配建议，用户确认后核销；多付金额明确选择留作预付。抵扣单要展示来源额度、限制和目标货款，不能点“付款”却没有真实支付。

对账单按日期导出，包含各类期初、期间增加与结清、期末余额及未结单据。预付款转类与核销有对应关系，汇总不重复累计；双方确认结果保留日期和凭据。供应商说余额不同，应逐项核对原因，不用一笔无说明调整强行对齐。

## 十、建议的数据对象与边界

| 对象 | 核心职责 |
| --- | --- |
| 往来单位档案 | 稳定 ID、供应商/客户角色、结算主体、联系人、付款账户及结算约定 |
| 采购订单 | 采购意向、约定数量价格、交货与付款条件；不自动等于全部入库 |
| 收货单及明细 | 实际验收数量、串码/批次、供应商、来源订单、暂估或确认成本 |
| 货款确认记录 | 明确已承担的货款、日期、到期条件及来源；这是内部记录，不是增值税发票 |
| 采购退换货记录 | 物流、串码去向、旧新货关联、应退货款的确认依据 |
| 供应商调整单 | 价保、返利、折让、补收、扣回等；申请/确认金额、范围、结算权利和成本性质 |
| 往来未结项 | 单一来源的待付款、可收现金、预付款、仅抵额度或保证金；保存剩余量及限制 |
| 实际资金记录 | 对方、日期、金额、账户、实际收付人、交易凭据；只记录真正的资金收付 |
| 核销/抵扣记录 | 多对多匹配、金额、来源和目标、操作人、冲销关联 |
| 成本调整及分配 | 关联原收货、串码/成本来源、仍在库存、销售或维修耗材的金额分配 |
| 对账记录与期初 | 截止日、各类余额、未结项、双方确认依据；与库存期初分开 |

往来余额由有效业务与核销计算，可缓存但不可直接手改；不采用一个可变的 `supplier.balance` 作为唯一事实。既有运营商佣金和工资模块通过来源 ID 关联，不复制同一笔应收或提成。

确认业务、生成往来及成本调整必须在同一事务中完成；核销验证双方剩余额、权限、同一主体及使用限制。提交保存幂等标识，避免移动网络重试重复收货、补差或退款。金额按分入账、成本单价保留足够精度，最后一笔分配处理尾差。

## 十一、落地顺序与历史数据

1. 第一批：供应商档案与稳定 ID、期初双向往来、采购/收货/付款解耦、预付及部分付款、退款、抵扣、多单结算、明细对账。一次普通进货依然一个简洁表单。
2. 第二批：采购退货、价保补差、暂估核价、串码成本调整、已售成本调整；支持简单来源清楚的普通商品，复杂移动平均价差经独立验证后开放自动分配。
3. 第三批：按用户确认规则接入提成补调，补齐活动返利、换货和代垫；借机/寄售在确认实际需要后增加专门流程，不冒充普通采购上线。

前两批构成用户所述业务的必要闭环，不能只做欠款列表而把调价停留在备注。数据结构从开始就支持多种来源，不靠后续手改余额补洞。

迁移之前备份现有数据、列出变更预览。原供应商名称合并到稳定 ID 需要人工核对，不凭相似名称自动归并；原采购、付款保留来源，不与新期初重复计账。

真实库存表只能证明库存数量和价值，不能据此推算欠哪个供应商多少钱，也不能编造原批次。上线日往来余额需另行收集：每家待付、对方应退、预付、仅抵额度、保证金及对应凭据；无法逐单追溯的以明确期初未结项记录，不能造历史采购单。

## 十二、必须通过的验收案例

1. 10 台各 2,000 元入库，付 12,000 元，确认全批补差 1,000 元并抵扣，待付准确为 7,000 元，没有虚增现金收入。
2. 同例 6 台在库、4 台已售，库存减少 600 元、已售成本减少 400 元；只补库存的协议则总额为 600 元。
3. 先付 10,000 元，只到 6,000 元货，核销后预付 4,000 元、待付 0；退回剩余预付时只增加真实到账现金。
4. 已付、未付、部分付三种采购退货均结算正确；待付 4,000 元与退货可退款 6,000 元抵扣后只剩对方应退 2,000 元。
5. 同型号来自两家供应商，只调整适用供应商的范围；混合移动平均库存缺乏来源时不伪造自动分配。
6. 价保截止日在库、确认前售出的手机，资格与成本去向分别正确；同一活动反复提交只产生一次补差。
7. 已获补差的货再采购退货、客户退货或发生补差撤回，库存、往来与成本不会重复受益或漏扣。
8. 一笔付款结多单、一单分次结算、多付留存、部分退款及仅抵额度都能追溯，退款和抵扣不混记。
9. 当前工资和历史销售快照不被直接覆盖；选择补发时按原规则及累计提成计算差额，部分退货不重复扣提成。
10. 同型号换机不虚增销售和货款，新旧串码可追溯；老板个人代付不误扣店铺资金账户。
11. 同单位兼供应商和客户可按协议抵扣，不同主体不能抵扣；运营商佣金应收不会被重复生成。
12. 仓库员不能越权确认补差或核销，员工不能读取供应商资金；确认过程报错全部回滚，重试不重复入账。
13. 期初与旧采购没有重复入账，任意日期对账单能由明细重建，冲销核销不会伪造反向转账。

## 十三、仍待用户确认

已向用户提出的三个关键问题：

- 调价通常仅补当时库存，还是按约定可覆盖指定批次及已售商品？建议允许逐次协议明确，不采用全局固定假设。
- 补差/返利可退现金，还是只抵以后进货？建议逐笔记录权利与限制。
- 已售商品后续补差增加的毛利是否补员工提成？建议先展示影响，由老板确认政策；尚未将此建议视作已同意。

进入实施时再补齐的资料与权限：现有供应商名单和期初各类余额、是否实际使用寄售/借机/保证金、店长的往来确认权限、复杂普通商品的成本分配口径。不要因此延迟已经清楚的基础流程建模，也不要未经确认写入假账款。
