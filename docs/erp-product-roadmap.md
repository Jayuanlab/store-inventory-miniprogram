> 本文保留升级前的评估快照，下面“当前代码”的缺陷描述属于当时状态，并非升级后仍全部存在。2026-09-06 已落地事务存储、身份权限、可信销售成本、多商品开单、原单退货、维修实际耗材、号卡佣金分账和工资模块；现状、验证命令及未实现事项见根目录 README。正式库存未重新导入。

评估日期：2026-09-06。依据：当前工作区代码、当前数据文件、已有真实库存核对报告、内存副本验证。

状态：产品与架构建议。用户已确认一家店、货均在店内，销售基本当场付清，采用微信、支付宝或现金；号卡同时有顾客售价和运营商佣金，需要分别记账；维修按本次实际消耗的维修件计算成本。佣金结算方式待进一步确认。本次没有修改应用逻辑或业务数据，也没有重新导入库存。真实库存数量引用自之前的导出核对，不代表今天实盘结果。

## 1. 产品判断

项目已经有了原生微信小程序、商品分类、期初导入、采购、销售、库存和日报的雏形，足以讨论操作习惯。下一步应把它做成适合聚友通信城的内部经营工具：员工能快速完成一笔业务，仓管能说清每件货的来去，老板能从日报追到原单和收付款记录。

目前最大的缺口是业务记录之间没有完整联动。界面提示成功、库存减少、收到钱、产生毛利，还不能被视为同一笔已经核对完成的业务。专业 ERP 的价值体现在这些记录一致、可查、可纠正，以及员工日常操作足够简单。

建议继续保留原生小程序和已确认的朴素界面，按完整业务流程逐段升级后台。采购、销售、库存、资金、权限和报表可以在同一个后端中按模块组织，当前规模无需引入微服务。

已确认的产品边界：仅供内部老板、店长、员工、仓库员使用；维修通过普通销售单收费；没有独立维修页面；开单以搜索商品和填写售价为主；暂不建设预警和异常分析模块。

根据本次回答，首版采用一个门店和一个默认店内库存地点，优先支持微信、支付宝、现金的当场全额收款；号卡销售及运营商佣金台账一起建设。多门店调拨、客户赊账、分期和复杂支付组合后置，采购是否需要供应商月结仍按实际情况确认。号卡佣金应收不等于顾客赊账，即使顾客当场付清，仍然可能存在尚未到账的佣金。

## 3. 四个角色每天怎样使用

下面是推荐的默认分工，店长授权范围可由老板调整；当前项目已有店长角色定义，但没有具名的店长账号。

| 角色 | 每天主要工作 | 默认首页 | 默认权限边界 |
| --- | --- | --- | --- |
| 老板：示例老板 | 看经营结果、查钱和货、确定价格及授权、处理供应商付款 | 今日销售、毛利、实收、退款、支出；可进入对应明细 | 全店经营数据、成本利润、人员授权、正式建账和更正 |
| 店长：待指定 | 组织当天销售、核对收款、处理退换货、查看员工销售 | 当天单据、收款汇总、当班交接 | 本店数据；成本利润、退款和改单权限由老板配置 |
| 员工：示例员工甲、示例员工乙 | 搜商品、扫码、销售收款、查本人单据；有技能者销售维修项目 | 快捷开单、本人今日销售、最近单据 | 可售库存、售价、本人业绩；默认看不到成本和全店利润 |
| 仓管：示例仓管 | 收货、录串码、盘点、采购退货；多地点时处理调货 | 收货、库存、盘点入口 | 库存及授权采购数据；默认不销售、不看全店利润、不管理账号 |

老板本人也可以开销售单。日常开单默认本人是操作人和销售人，无需反复选择姓名。若老板替示例员工甲补录业务，分别记录“录单人：示例老板”和“销售人：示例员工甲”；修改销售归属必须有授权并留记录。确认收款的人也可以与销售人不同。

员工工资与销售提成已确定纳入首版。不同商品可以按件或按毛利百分比提成，工资由基础工资加提成组成；老板及所有店长均可维护底薪和规则，老板查看全员工资。销售时记录规则和计提结果快照，销售完成当月计提、退货发生当月扣回，工资按员工及月份汇总，具体见 `docs/payroll-domain-model.md`。

## 4. 先建立几条清晰的数据关系

### 商品资料与库存

商品资料回答“卖什么”，库存余额回答“某地点还有多少”，串码实体回答“具体是哪一台”。商品名称、售价、分类发生变化时，已经完成的单据保留当时的名称、售价、成本和分类快照。

| 概念 | 建议内容 | 约束 |
| --- | --- | --- |
| 分类 | 原有一级、二级、三级目录 | 保留旧目录路径用于迁移核对；品牌、供应商另存独立字段 |
| 商品 SKU | 内部 ID、原商品编号、名称、简称、规格、单位、默认售价、启停状态 | 内部 ID 稳定；原编号按文本保存；被单据引用后用停用代替删除 |
| 商品性质 | 实物、服务 | 不由“维修”这个分类名称决定 |
| 库存方式 | 不管库存、按数量、按串码 | 显式配置；已有余额时转换方式必须对齐库存明细 |
| 库存余额 | 商品、地点、数量、库存成本金额 | 库存变化有来源单据；服务商品没有虚构的库存数量 |
| 串码实体 | 商品、地点、主串码、其他标识、状态、入库成本、出入库来源 | 手机 IMEI1/IMEI2 属于同一台机器；号卡 ICCID 和手机号不是同一种标识 |
| 库存流水 | 来源单据及行、地点、数量增减、成本增减、业务时间、操作人 | 可由期初和后续流水复核余额 |

旧分类里可能同时混有品类、品牌和供应商。先保留来源目录，再建立独立字段与映射；不要通过重命名目录来偷偷改变进销存规则。导入时无法确定的字段保留待确认，不根据名称推断号码、运营商佣金或手机串码。

### 维修继续在普通销售单中完成

“尾插维修件”可以是有库存的实物 SKU；“尾插更换服务”可以是不直接占库存的服务 SKU。店员都通过同一个开单入口选择。以维修为分类不应直接决定是否扣库存。

用户已经选择按本次实际消耗的屏幕、电池等维修件核算成本。后台应保存材料 SKU、数量、实际出库成本以及关联的销售明细；材料扣减与销售完成在同一次入账中执行。下述两种操作方式都遵循实际材料成本，同一份材料只能扣减并计成本一次。

建议支持两种实际操作方式：

- 门店习惯按维修件收费：选“尾插维修件”，填包含安装的总售价 80 元，扣 1 个成本 18 元的尾插，销售毛利 62 元。
- 门店习惯按维修项目收费：选“更换尾插”，收 80 元，关联本次消耗的尾插成本 18 元及实际外修费用。材料只记成本消耗，不再额外算一次销售收入。

常用项目可以带出默认材料，操作人只在本次材料不同时修改。无需恢复独立维修页面。预设项目成本可以辅助报价，正式毛利依据本次材料出库成本计算。人工成本只有在门店明确核算规则后加入，避免与工资费用重复计算。

### 号卡需要把商品与收入来源说清

实体卡可以有库存和串码；套餐档位、业务名称、预计返佣是另外的属性。像“利润100元”的名称不能自动证明已经收到了 100 元，也不能证明它本身是需要计数的一件库存。

用户已经确认号卡同时有售价和返佣，因此这部分进入首版：将业务办理记录关联到销售明细，另外记预计佣金、确认佣金、实际到账和扣回。预计佣金先单独展示，确认和结算依据由渠道规则决定，不能默认混入当日实收。

| 号卡业务记录 | 用途 |
| --- | --- |
| 关联销售单、办理日期、销售人 | 追溯这笔业务由谁办理、对应哪次销售 |
| 运营商、结算渠道、套餐、卡标识 | 确定向谁核对佣金；套餐月租不自动等于门店售价 |
| 顾客实付及收款账户 | 微信、支付宝、现金收款，归入顾客销售结算 |
| 预计佣金 | 待渠道核实的预计收益，单独展示 |
| 已确认佣金及确认依据 | 经结算单等依据确认的金额，形成可追踪的佣金应收 |
| 到账明细及到账日期 | 可多笔到账，按到账日统计；不会再生成一笔商品销售 |
| 扣回或调整及依据 | 关联原业务调整，保留原始记录和变更原因 |

例如某卡顾客实付 50 元、预计佣金 100 元，今天实收是 50 元，预计佣金单列 100 元。之后渠道确认并到账 100 元，记录佣金确认和收款，不能再增加一张 100 元的普通销售单。如果顾客支付的款项含代收首充话费，需要进一步标明代收与本店价款，不能仅凭总收款判断本店收入。

### 销售、收付款与成本

建议建立销售单及明细、采购入库单及明细、收付款记录、收付款与单据的分配关系、退货单及明细。不同单据复用编号、状态、时间、附件等基础规则，但保留各自的业务约束。

一张销售单可以有多种收款，一笔收款可以补结历史欠款。录入“微信收款”代表内部记账，不代表小程序已经向微信支付平台核实到账。第一版可以由收款人确认，之后再根据需要接商户账单核对。

采购进货成本与供应商付款也分别记录：货已入库但尚未付款时形成应付，不能因为没有付款而遗漏库存。

## 5. 每天的核心流程

### 进货

选择供应商和收货地点 → 搜商品或新增商品 → 录数量、实际进价、必要串码 → 确认收货 → 生成库存流水及应付 → 记录本次付款。

普通门店先采用一次确认完成采购入库，减少操作步骤。只有实际存在先下单后分批到货，才增加采购订单及分批收货。赠送进货、运费是否分摊到货品成本需要约定，不应由系统猜测。

建议普通配件采用移动加权平均成本。手机若按逐台串码管理，则保存逐台实际成本；历史只有汇总数量和均价时，先作为期初汇总余额。新采购逐台录串码，旧库存通过专项补录转换，不能直接开启串码开关后让已有库存变得无法销售。

### 销售

搜索商品或扫描条码、串码 → 填实际售价 → 确认销售和收款 → 查看单号及结果。

默认数量 1、销售人本人、常用收款方式预填。买多个商品时点“继续添加”，不用为手机、壳、膜分开开单。只有需要串码的商品才显示串码，只有赊账、售后留联络信息等场景才要求客户信息。

搜索优先精确匹配串码、条码和商品编号，再匹配完整名称、简称和型号，最后使用别名。保留用户输入的型号和容量限制；不要因识别到“苹果”等词就丢掉剩余搜索条件。结果显示规格、地点和可售数量，提供继续加载；现有截断到 20 条且没有更多结果入口的方式需要调整。

提交中的按钮防连点；服务端用请求编号防止重复开单。请求超时属于结果未知，先查询该请求的原单；确定未入账后才允许再次提交。只有服务器确认后显示完成，本地草稿与已入账单据采用不同状态。

### 查单与退货

单据入口支持按日期、商品、串码、单号和销售人搜索，并可以打开完整详情。售出的串码仍可通过历史查询找到，不能只存在于可售列表中。

退货从原销售单选择商品和数量，可只退充电器而保留手机。系统同时处理退货金额、原销售成本冲回、可退数量、货物去向和退款记录。损坏商品回待处理地点，不直接增加可售数量。维修服务退款不凭空增加实物库存。

草稿可以修改；已入账业务通过有来源的更正或退货处理。错误开单取消与客户实际退货应有明确区别，避免同一商品被重复退款或重复回库。

### 盘点与日结

仓管按分类或货架逐步盘点，系统带出账面数量，仓管填实盘数量并确认差异；串码商品可扫码核对。差异生成调整单，不直接覆盖余额。盘点开始时记录时间范围，期间发生的销售或收货必须纳入差异计算。

店长或老板核对当天各收款方式及现金实点，确认收退款、费用、旧欠款回收和供应商付款。现金账户与微信、支付宝等收款渠道分开，渠道到账银行的转账不能再次算销售收入。

## 6. 老板日报的口径

日报先回答“今天卖了多少、毛利多少、收了多少钱、付了多少钱、钱和货能否追溯”。金额可点击查看组成该数字的单据，默认以北京时间营业日统计。销售日、收款日、结算到账日各自保留。

| 指标 | 第一版建议定义 |
| --- | --- |
| 当日销售额 | 当日已入账销售单金额，不含未提交草稿 |
| 当日退货额 | 当日入账的退货金额，保留原销售日期 |
| 销售净额 | 当日销售额减当日退货额 |
| 销售毛利 | 销售净额减相应销售成本，退货按原销售成本冲回 |
| 当日实收 | 当天确认的收款，包含历史欠款回收；不由销售额推算 |
| 当日退款 | 当天实际确认的退款，与退货发生日可能不同 |
| 当日费用 | 按已约定经营口径记录的房租、运费等费用，区别于采购付款 |
| 应收、应付 | 截至查询日期尚未结清的客户欠款和供应商欠款 |
| 库存资金 | 截至查询时点的库存成本余额 |
| 员工业绩 | 按销售归属及其关联退货汇总；录单人单独保留 |

“毛利减已记录费用”可以作为经营参考，但在房租、工资、佣金等未完整归集前，应明确为该口径下的经营结余，不能标成已经核实的净利润。现金收支余额也是另外一个指标。

例：9 月 6 日卖出 2000 元、收 1500 元，另收回昨日欠款 500 元。当天销售额 2000 元，当天实收也为 2000 元，但两者来自不同记录，该新单仍欠 500 元。9 月 7 日收齐后，只增加 9 月 7 日收款，不重复增加销售额。

## 7. 开发架构建议

```text
微信小程序：开单、查单、收货、盘点、经营查看
                  |
             统一业务 API
                  |
账号授权 | 商品资料 | 库存串码 | 采购销售 | 收付款 | 报表
                  |
        PostgreSQL 数据库与版本化迁移
                  |
          自动备份及独立恢复环境
```

建议保持 Node.js 技术方向，在后端逐步使用 TypeScript 约束接口和数据，采用 PostgreSQL 管理正式数据。数据库事务可以让相关数据库更新一起提交或一起回滚，行锁可以控制同一库存的并发修改；需要应用正确实现事务边界、锁定顺序和重试规则。[PostgreSQL 事务文档](https://www.postgresql.org/docs/current/tutorial-transactions.html)、[并发锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)。

例如确认销售时，单据、库存扣减、串码状态、成本快照和内部收款记录在同一数据库事务内完成。外部支付平台的真实扣款不能被本地数据库事务回滚；将来接入支付时，应另做支付状态、回调去重及对账。目前内部记录收款不需要引入完整支付平台。

建议按以下能力改造现有实现：

- 统一认证和权限入口：所有请求由登录会话识别人，接口分别检查动作权限、数据范围和成本利润字段权限。
- 统一商品资料：导入、新增、修改使用相同的商品性质、库存方式及校验规则。
- 统一过账入口：在后台一次完成单据、库存、成本和账款的关联更新；前端不能另算一套实际库存和毛利。
- 金额使用定点数或明确的最小货币单位；库存均价需要较高小数精度，保存库存成本金额并约定舍入方式。对负数、非有限数、数量与串码不一致进行输入校验。
- 核心表增加唯一约束、外键和必要索引；库存使用商品加地点定位，查询支持分页。单号、请求编号、串码标识各有清晰的唯一范围。
- 开发、测试、试用和正式数据隔离，测试不能默认指向店铺使用的接口或账套。备份必须能在另一环境实际恢复。
- 小程序使用可配置的服务地址，正式运行需要店员手机能够访问的服务。当前 `127.0.0.1` 只指向运行客户端的设备，不能作为员工真机的统一后端地址。

微信身份绑定员工、正式网络配置等实施细节在开发阶段按微信官方要求核对。本次官方文档页面未能抓取，不将未读取页面的具体平台限制作为本次评估证据。

电脑管理端作为后续可选项：当老板或仓管经常批量改商品、处理 Excel、核对供应商账款时，它会比在手机上做表格操作更合适。先复用同一套后台接口，等待实际操作需求明确后再增加，避免同时维护两套业务规则。

## 8. 开发顺序与完成标准

### 第一阶段：可信的单店试用版

完成真实身份与服务端权限、数据库迁移、移除业务失败后的模拟成功、正式与测试隔离、带预览及核对的期初建账、实际进价入库、销售及成本快照、维修实际材料消耗、微信/支付宝/现金收款记录、查单、基础原单退货、号卡佣金台账及基础日报。同步完成商品提成规则、员工底薪、逐笔提成和月工资单，老板可查全员工资，员工仅查本人。已有页面可以继续复用，批量操作等体验在此基础上改善。

验收时由示例仓管完成收货，示例员工甲、示例员工乙各用自己的手机完成销售，由具备权限的人处理原单退货；示例老板查看相同单据和日报，示例仓管能核对对应出入库记录。另外完成一笔号卡顾客收款和后续佣金到账，确认日报不会重复计收入。普通当场收款的销售应保持少量必填项。

### 第二阶段：连续经营所需的管理能力

完善供应商付款及采购退货、盘点调整、费用录入、日结交接、多商品开单、常用搜索和导出，补充实际需要的号卡结算批次管理。客户赊账和组合付款目前不是主要场景，可在实际出现时再增加。

验收时连续试用建议至少 7 个营业日，每日核对库存变化与收退款，并检查跨日欠款、退货、成本变动；该建议是试用范围，不是工期承诺。

### 第三阶段：按真实业务补行业能力

根据经营需要增加运营商结算表自动匹配、维修材料默认组合、以旧换新、电脑批量管理。号卡基础佣金台账、员工提成及工资已纳入第一阶段；多店调货待未来出现多店经营需求再建设。

预警、复杂审批流和大型经营分析暂不进入范围。必要的数据校验、权限控制和错误提示属于可靠记账的基础能力，应随业务实现。

## 9. 用这些经营场景验收

| 场景 | 应有的结果 |
| --- | --- |
| 两人同时卖最后一台手机 | 只有一个人能完成，另一人看到库存已变化；不出现两张都成功的销售单 |
| 连点提交或提交后网络中断 | 最终只产生一张销售单，可凭同一请求恢复原结果 |
| 员工修改请求中的身份或成本 | 后端仍以真实登录身份和服务端成本为准 |
| 同型号手机第二批进价改变 | 销售及库存成本遵循选定算法，旧销售毛利保持原快照 |
| 手机、壳、膜一起卖 | 一张单可完成，分别扣库存；只退壳时手机不回库 |
| 换尾插收 80 元、材料成本 18 元 | 收入只计 80 元，库存只消耗一次材料，成本只记一次 |
| 今天销售、明天收余款 | 两天销售与收款按各自日期统计，不重复销售 |
| 已入账后再次上传期初表 | 不清空销售和采购；引导走资料更新或盘点流程 |
| 手机有两个 IMEI | 对应同一台库存实体，不能作为两台分别销售 |
| 凌晨开单、改商品名称或分类 | 首页与日报营业日一致，历史单据保留当时快照 |
| 从备份恢复到独立环境 | 单据、库存、串码、收付款可核对一致 |

上线不以“页面都能打开”为完成标准，而以这些流程能由不同角色实际跑通、账能核对为标准。系统中每个余额都应能说明来源，每张已完成单据都应能查到经办人和后续处理记录。

## 10. 需要用户回答的关键问题

已确认：一家店、货均在店内；微信、支付宝或现金基本当场付清；号卡售价和运营商佣金需要分别记账。已经据此收缩首版范围，并将号卡佣金台账前移至第一阶段。

维修成本已确认按本次实际消耗的维修件计算，已经纳入第一阶段的库存和销售联动。仍待回答：佣金是一次结清、分期且可能扣回，还是先逐笔记应收和到账。回答前先保留预计、确认、到账和调整的独立记录，不预设结算周期或自动生成返佣计划。

在进入具体实现前，再按需要逐项确定：手机是否必须逐台 IMEI、现有串码如何取得；维修件是单独卖还是按项目带材料；店长人选和退款授权；采购是否存在月结；是否每天交班对账；谁负责商品资料和正式期初核对。无需一次回答全部问题，可以围绕真实单据逐个确认。

建议下一次开发按“某件真实商品入库 → 员工销售 → 记录收款 → 老板查单及日报 → 原单退货”的完整场景推进。每完成一个场景，就让实际使用者验证，再扩展到其他业务。
